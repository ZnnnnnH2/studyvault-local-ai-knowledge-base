## 二、影响演示和功能完整性的问题

### 1. 打开会话后会反复请求列表和详情，需要优先修复

位置：[static/app.js:8](D:/Database/hw2/static/app.js:8)、[static/app.js:9](D:/Database/hw2/static/app.js:9)。

调用链为：

```text
openConversation(id)
  → loadConversations()
    → 若 state.selected 非空，openConversation(state.selected)
      → loadConversations()
        → 持续重复
```

用原文件中的函数和最小 DOM/fetch 替身复现：只调用一次 `openConversation(1)`，没有进一步用户操作，仍连续产生交替的详情/列表请求。测试在第 11 次请求暂停返回，阻止继续循环。

实际影响：会话内容和列表反复重绘，增加后台负担，并可能打断消息批注输入。应拆开“加载列表”“加载详情”“更新选中样式”，消除双向调用。

证据：[HW2_FRONTEND_REVIEW_EVIDENCE.json](D:/Database/hw2/docs/HW2_FRONTEND_REVIEW_EVIDENCE.json)。这是函数级复现，未进行真实浏览器画面验收。

### 2. 后端有分页，前端只能显示默认前 20 条

位置：[app.py:381](D:/Database/hw2/app.py:381)、[static/app.js:8](D:/Database/hw2/static/app.js:8)、[static/index.html](D:/Database/hw2/static/index.html)。

API 支持 `limit` 和 `offset`，默认 `limit=20`；前端没有分页状态，没有传 `offset`，也没有“下一页/加载更多”控件，未使用返回的 `total`。因此同一筛选条件下第 21 条起的记录无法通过翻页浏览，须进一步缩小搜索才能找到。

这不是“分页放在前端执行”的问题，而是后端分页尚未接入页面。

### 3. 复习卡 API 可用，网页缺少创建入口

位置：[app.py:430](D:/Database/hw2/app.py:430)、[static/app.js:9](D:/Database/hw2/static/app.js:9)、[static/app.js:10](D:/Database/hw2/static/app.js:10)。

`POST /api/reviews` 可以创建复习卡，“复习队列”也有答对/答错按钮。但消息页面只有批注输入，没有“加入复习”按钮或创建卡片表单，前端没有调用创建接口。普通用户无法完成“读消息 → 整理为复习卡 → 复习”的页面流程。

现有报告第 4 个演示步骤要求“在数据库中创建复习卡”，也说明这里仍需人工操作。应在消息旁接入创建入口；演示数据还应包含已到期卡片，因为新卡默认明天到期。

### 4. 报告中的历史数据确实附带了，但首次启动不能恢复同样结果

位置：[README.md:23](D:/Database/hw2/README.md:23)、[staging/structure_and_sync.py:7](D:/Database/hw2/staging/structure_and_sync.py:7)、[app.py:277](D:/Database/hw2/app.py:277)、[app.py:485](D:/Database/hw2/app.py:485)。

### 5. 继续同一会话后再次扫描，不会追加新消息

位置：[app.py:281](D:/Database/hw2/app.py:281)。

只要来源会话 ID 已存在，`import_file()` 就直接返回 `SKIPPED`。实测原文件有 2 条消息，第一次导入成功；追加到 3 条后再次扫描，数据库仍只有 2 条。

PPT 没有明确要求增量同步，因此这不是独立的必做项；但需要在产品和报告中说清“每个会话仅导入一次”，或实现按消息稳定标识/序号去重追加，否则持续学习记录会不完整。

## 三、其他建议与边界

- 课程、知识点、标签的表和关系已存在，导入也能自动归类；目前页面主要是展示分类结果，缺少人工调整课程、标签、知识点的入口。第 18 页是参考功能，因此应按最终自己定义的需求决定是否补齐，而不是为凑功能强制扩展。
- `/api/stats` 的知识点统计使用 `COUNT(cp.conversation_id)`，即使后续 `LEFT JOIN conversation` 的用户过滤未匹配，仍会计数。隔离测试增加另一用户的一条关联后，当前用户应为 25，实际统计为 26。位置：[app.py:464](D:/Database/hw2/app.py:464)。当前是固定演示用户，优先级低于页面与交付问题；不需要据此扩展成多角色系统。
- 当前已有 JSON、结构化 JSONL、人工标注快照和课程 Markdown 导出；未发现统计结果文件下载入口。如果最终需求写成“导出统计信息”，应补统计导出；也可以在自定义需求中清楚说明统计展示与会话资料导出的范围。
- E-R 图参考示例把课程、标签联系到消息；hw2 把它们联系到会话。PPT 允许自行设计，不能仅凭这一差异判错。报告宜解释为何以会话作为归类单位，以及一段会话跨多门课程时如何处理。
- 报告应突出若干真实的课程学习案例，说明“原始问答 → 整理归类 → 纠错批注 → 复习”的效果；记录总量本身不能替代学习场景的验证。
- Text2SQL、网页平台直接抓取、复杂多角色权限，都不是当前选题必须补做的统一要求。
